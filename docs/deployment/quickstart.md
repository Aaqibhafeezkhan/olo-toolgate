# Quickstart deployment and recovery

Quickstart runs Control, Gateway, the console and a real native executor in one non-HA local evaluation image. SQLite is the default; external PostgreSQL uses separate migration, runtime and protected platform principals. All execution requires current Control. There is no local policy ALLOW or Redis authorization fallback. See [multitenant deployment and qualification](multitenant.md) for UUID initialization, shared subdomains and release gates.

Build and verify with `python tools/quickstart/check.py --build`. Use `--image IMAGE`, `--postgresql`, `--no-browser` or `--client-assets VERIFIED_DIRECTORY` as needed. The isolated gate records installation, real native CSR/mTLS, verified disabled-user intake, independently reviewed grants, HUMAN/SERVICE/ASK effects, exact retry, revocation, reviewed import/shadow, restart and browser accessibility. Small-fixture latency is measured in `build/quickstart/smoke.json`; it is not an enterprise throughput promise.

Run the image with a persistent `/data` volume, read-only root, dropped capabilities, no-new-privileges, a restricted `/tmp` and loopback ports 8080/8443. The verified gate uses 2 CPUs and 1536 MiB. [Compose helpers](../../deploy/compose/QuickStart/README.md) retain the volume through update/undeploy. For this repository's persistent debug environment, run `debug/start.bat`; it validates the candidate before replacing the debug container.

First boot installs protected default groups, separate local admin/reviewer-1/reviewer-2 identities and zero runtime rights. Tools and the local Agent begin disabled. Retrieve each bootstrap password privately from `/data/credentials.json` or its `/data/bootstrap-password*` file. No account must change its password at first login; any account may change it later at login, except accounts shown on the login page. Password-free local mode changes login only. The new native Device appears pending: review its code/key, approve its connection, then independently review group grants and definitions. Device approval creates no Agent credential. Keep Agent configuration outside the diagnostic mimic script, which only calls and logs bounded output.

The first setup user (`admin`) cannot be deleted or disabled, even after another
Super Admin is assigned. Its initial email is `admin@admin.com`; set
`TOOLGATE_ADMIN_EMAIL` on the container before first boot to override it. Restarts
and upgrades never apply this variable again or change an existing email. Edit
the user's email in the console afterward; its stable `admin` login is unchanged.
Super Admin authority comes from an enabled Management Role with `SUPER_ADMIN`
classification on an enabled Team. Any enabled member receives the same management
privileges; other roles retain their editable rules and runtime grants.

For human access, enable the verified User and supply a complete Team/Human Role grant for Tool Group, action, bound Device Group, resources and conditions. SERVICE additionally needs explicit workload binding, Agent Group capability and SERVICE grant. Delegated execution additionally requires a verified human session and matching Team/Agent Group delegation. Management Roles do not create runtime rights.

Optional native downloads require a verified asset manifest included at image build. Unsigned Windows installers are refused. Keep private configuration and data outside Git; do not mount host home directories, Docker sockets or arbitrary host shells into this evaluation image.

Use the stopped supervisor's offline backup command under the exclusive volume lock. Restore requires an independent empty destination, exact manifest with complete current key inventory, two external reviewer signatures, separately pinned trust, live revision/epoch/sequence/session/credential floors and post-backup retirement evidence. It quarantines old authority, retires identity signers and leaves the UUID SUSPENDED while retaining spent nonces/audit/history. Re-establish reviewed management recovery, fresh identity custody and intended runtime grants before reopening traffic. See [tenant recovery](../control-plane/tenant-recovery.md) for both storage modes and partial-restore fencing. Copying an old database over live state is not a supported rollback.

Packages and releases come back exactly. A backup holds every uploaded package with its bytes, the Tool Host deployments and their documents, each deployment profile's recorded status and the fleet releases, and restore keeps them unchanged. Queued work expires. Dispatched or executing work becomes `OUTCOME_UNKNOWN` and requires reconciliation before retry; finished calls retain their durable results. After reviewed activation, Control applies its deployment profile through the same provisioning service: the recorded packages are already installed, so it imports, redeploys, substitutes and grants nothing, and a profile package that is not available stays visibly pending or failed. Client-tool images live in your registry; keep them there, or in a verified mirror, with the backup.

## Initialize file, trust volume and generated credentials

Tenant identity is an immutable installation UUID; the alias is only a lookup label.
Reusable initialize files should omit `tenantId` and set `tenantName` for display
(non-blank, at most 256 UTF-16 code units). `TOOLGATE_TENANT_NAME` overrides the file
on first installation, with `Quickstart` as the default. The name is persisted and
used for Control's organization metadata and console display alongside the UUID.
Changing these inputs later does not rename an initialized tenant or replace its ID.

Set `TOOLGATE_INITIALIZE_FILE` to a configuration snapshot (the `snapshot` of an export, or the whole import envelope) to apply it once on a fresh `/data` volume. Its records are merged into the installation snapshot; the `admin`, `reviewer-1` and `reviewer-2` users, the installation team and the Super Admin role always stay as installed. Team members from the file are added to existing members, and each `requiredIdentities` id that does not exist becomes a disabled placeholder user added to its teams. The file's `settings` reach Control as `TOOLGATE_GATEWAY_NAME`, `TOOLGATE_SETTINGS_AUTO_APPROVE_DEVICES`, `TOOLGATE_SETTINGS_AUTO_APPROVE_DURATION_DAYS`, `TOOLGATE_SETTINGS_AUTO_APPROVE_OWNER` and `TOOLGATE_CONFIG_REQUIRED_REVIEWS`; a non-empty container variable of the same name wins.

Every enabled user in the file can sign in locally with a random password. Every workload binding in the file gets a random static token; its hash goes into the binding and into the Gateway credentials, and the binding's calls use the first execution binding its agent groups' CAPABILITY grants cover. Everything generated is written once to `/data/credentials.json` (mode 0600, never logged): `users` (with admin and reviewers), `agents` (`agentId`, `workloadBindingId`, `token`, `userId`) and `claimToken`. Users marked `showOnLogin` are listed, with their passwords, by the unauthenticated `GET /api/quickstart/v1/login-hints`, together with `refreshAt` from `TOOLGATE_DEMO_REFRESH_AT`. When `TOOLGATE_LOGIN_HINT_AGENT` names an agent in the file, each listed account also carries that agent's token as `agentToken`, so a shared demo shows the token visitors connect their agents with; reauthorizing that agent's workload updates the listed token, and no other reauthorized token is stored.

A `visitorPool` creates `TOOLGATE_DEMO_ACCOUNT_POOL` (default 50) disabled accounts `<prefix>001` …, each in the pool's team with claims assigned round-robin, an agent in its agent group, a disabled DELEGATED workload binding and an identity binding. Control holds at most `TOOLGATE_CONTROL_MAX_RECORDS` (512) records: the installation's records, the Tool Host, the file's `reservedRecords` and five records per pool account must fit, otherwise Quickstart refuses to start and names the largest pool that fits. `POST /api/quickstart/v1/demo-accounts/claim` with `Authorization: Bearer <claimToken>` and `{"requester":"<id>"}` returns `username`, `password`, `agentToken`, `consoleUrl` (`TOOLGATE_PUBLIC_CONSOLE_URL`), `gatewayUrl` (`TOOLGATE_PUBLIC_MCP_URL`, default the device Gateway origin plus `/mcp`) and `expiresAt`. A repeat claim by the same requester returns the same account with new credentials and revokes the previous ones; an account is never handed to another requester while this `/data` volume lives; an empty pool answers 409 `POOL_EMPTY`. A Super Admin can issue a fresh token for any workload binding with `POST /api/quickstart/v1/workloads/{id}/reauthorize`; it is shown once.

New agent tokens take effect without a restart: the supervisor rewrites the Gateway credential file atomically, sends the Gateway SIGHUP and waits until the Gateway management endpoint `GET /v1/credentials` reports the digest of that file. The Gateway validates a new file completely and keeps its current set on any error.

Mount an optional second volume at `/trust` to keep `device-ca.crt`, `device-ca.key`, `server.crt`, `server.key` and the TLS trust store across a reset of `/data`: enrolled clients keep trusting the server, while everything else, including the login signing key, is regenerated, so every earlier session and token is rejected. Public copies of the certificates stay at `/data/keys/`. The offline backup covers `/data` only; back up `/trust` separately. Do not add `/trust` to an existing installation whose keys live in `/data/keys`: a new CA would be created.
