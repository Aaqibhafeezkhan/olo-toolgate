# Tenant discovery v2

The live Control endpoint and native service use v2. Installer setup verifies the signed document over independently authenticated HTTPS before persisting the tenant UUID and canonical Control origin. Fresh journal format 3 stores the manifest and monotonic discovery trust together; old development journals are refused without conversion. Qualify shared production hosting using the [multitenant deployment guide](../deployment/multitenant.md) and its runtime and recovery checks.

V2 follows the existing Fleet compact [JWS pattern, RFC 7515](https://www.rfc-editor.org/rfc/rfc7515.html#section-3.1). Its JSON envelope contains only `jws`. The protected header requires `alg=RS256`, `typ=toolgate-discovery+jws` and a bounded key ID. Unknown header fields, alternate algorithms, remote key URLs, duplicate JSON members and noncanonical base64url are rejected. The message type and separate signing keys apply the purpose-separation principles in [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.11).

The signed payload contains protocol version 2, a canonical UUID, server identity, organization, canonical service URLs, verification URI, minimum client version, issuance/expiry, key-set version, a public-only discovery [JWK Set](https://www.rfc-editor.org/rfc/rfc7517.html#section-5) and independent tenant device-CA metadata. RSA keys have 3072 or 4096 bits and exponent 65537. Device CAs bind the same UUID in their subject organizational unit, use a self-signed SHA-256/RSA root with path length zero, and cannot reuse discovery public-key moduli. Exactly one device authority is active, selected by its certificate-DER SHA-256 key ID; an optional second authority is read-only.

The signed issuer is `urn:toolgate:tenant:<UUID>`. Signed audiences contain the registered Control and Gateway HTTPS origins, which may differ. The producer checks these against the tenant runtime profile; verifiers require the selected origin to be an audience and the configured/stored UUID to match. Normalized duplicate origins are rejected. Initial trust requires independently authenticated HTTPS; a self-signed discovery document received from a page is insufficient. Subsequent signatures must continue from protected local keys. Helpers return new trust state only after full verification. The eventual native integration must validate the requesting console origin and tenant before exposing health, approval codes or device proof.

Key rotation requires preannouncement. Starting with key A at generation 1, publish A and B at generation 2 signed by A. Clients that verified this update can accept B signatures at generation 2. Retire A by publishing B alone at generation 3 signed by B. An unannounced signer, an omitted/revoked signer, a changed key set without a generation increase, lower generation or older issuance time fails. Key-set order has no significance. Metadata lifetime is at most five minutes. Payloads are bounded to 64 KiB and the compact envelope to 128 KiB.

The shared public interoperability corpus covers this rotation sequence, tenant/origin mismatch, signature corruption, wrong message purpose, algorithm substitution, remote-key headers, CA/discovery key reuse, v1 downgrade, alias IDs and expiry. `tools/tenancy/generate_discovery_vectors.py` generates these public vectors using temporary in-memory test keys; it writes no private material. Both Java and Rust consume the same corpus, alongside complete structural valid/invalid fixtures.

Protected [per-tenant mounted private-key custody](tenant-identity-custody.md), operator publication and active-key selection now feed live serving. The native service uses only v2 transport, checks certificate subject and identity URI claims, and persists tenant/key continuity before enrollment. Chrome can assert an optional canonical `expectedTenantId` for Connect, health, enrollment and proof. The assertion is never a destination selector or authorization credential. Tool Host discovery trust, Gateway public forwarding, rotation refresh and full cross-tenant qualification remain phase 4 work.
