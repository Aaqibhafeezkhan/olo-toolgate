# Tenant vault custody

Vault values use a random AES-256 encryption key per tenant. A separate random
tenant key authenticates idempotency digests, so encryption-key rotation preserves
exact retries without storing a dictionary-testable secret hash. Neither key is
derived from the public tenant UUID. The database stores wrapped keys only, with
non-null tenant ownership and forced PostgreSQL RLS. Runtime credentials can read
wrapped metadata; inserting, rewrapping or retiring keys requires the platform role.

The supported wrapping backend is an operator-managed local KEK ring using JCE
AES-256-GCM. Set `TOOLGATE_CONTROL_VAULT_WRAPPING_KEY_RING_PATH` to an absolute,
protected JSON file with exactly `formatVersion: 1`, `currentKeyId`, and `keys`.
`keys` maps operator-chosen IDs to base64 encodings of 32 randomly generated bytes.
IDs contain 1–64 letters, digits, underscores or hyphens and start with a letter or
digit; at most 16 wrapping keys may be configured. `currentKeyId` must name a key.
This file is secret material: supply it through protected deployment custody,
outside tenant imports and database backups. Helm's `control.vaultKeyRingSecret`
projects the `key-ring.json` key of an existing Kubernetes Secret with mode `0440`.

Quickstart creates its ring once as `/data/keys/vault-wrapping.json` with mode
`0600`. The platform initialization transaction provisions the tenant's wrapped
keys before activation; a rollback removes them with the rest of the seed. An
absent ring disables vault custody. Runtime writes never create missing keys.
The removed raw-key setting `TOOLGATE_CONTROL_VAULT_KEY_PATH` is rejected. Select
fresh empty storage for pre-release databases or raw-key Quickstart data; there
is no conversion or fallback reader.

Secrets store monotonically increasing secret and encryption-key versions. The
`TGVAULT1` envelope authenticates the format, purpose, tenant UUID, secret name,
secret version, tool group, device group and key version using an unambiguous JSON
array. Wrapped-key context independently binds tenant, purpose, version and the
configured wrapping-key reference. Unknown references, unsupported formats,
swapped envelopes and retired keys fail closed. References select only configured
provider keys, never filesystem paths or network locations from a database row.

Every delivery checks current tenant admission, certificate, executing invocation,
consumed fence and authorized group bindings before unwrapping a tenant key. There
is no reusable plaintext DEK or secret cache. Management listing returns authorized
references only; discovery and the browser extension receive no vault values.

`TenantRegistry.maintainVault(...)` is the protected platform operation used by
operator tooling. It serializes against admitted tenant writes, checks the expected
key version, and accepts a unique request ID for exact retry. Its operations are:

- `ROTATE`: generate a new tenant encryption key, retain the independent retry key,
  and re-encrypt the bounded set of current-format secrets. The old encryption key
  becomes `READ_ONLY`. Any failure rolls back all keys, envelopes and authority.
- `REWRAP`: wrap non-retired tenant keys under the configured current KEK, retaining
  the tenant encryption keys and secret ciphertext. Deploy the ring containing both
  old and new KEKs first; remove an old KEK only after all affected tenants have
  been rewrapped and verified.
- `RETIRE`: retire an old, read-only encryption-key version only when no current
  secret references it. An active or retired key cannot be revived by this path.

These operations audit the change and advance tenant authority/outbox state, so
old invocation authority cannot survive rotation. They leave other tenants' keys,
ciphertext and retry state unchanged. Upstream credential replacement is a separate
authorized secret write, which creates a new secret version. Deletion and key
destruction remain explicit offboarding/recovery work; disappearing from a manifest
does not destroy customer keys.

A shared KEK and the Control process that can unwrap several tenants remain a
platform trust boundary. Tenant DEKs contain accidental data/ciphertext mixing;
they do not contain full compromise of that process or its provider credentials.
Use separate application credentials/deployments and tenant-dedicated wrapping
custody when that stronger boundary is required. `VaultWrappingProvider` defines
the integration boundary for external KMS backends; none are claimed implemented.
Shared-host and release qualification are still tracked in `plan.md`.

Discovery continues using the development CA-signed protocol until the separate
server/client discovery-v2 milestone.
