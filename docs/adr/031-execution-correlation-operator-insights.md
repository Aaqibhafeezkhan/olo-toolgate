# ADR-031: Execution correlation and operator Insights

**Status:** Proposed

The delivery plan is [plan.md](../../plan.md). This record fixes the decisions that plan's step 1 requires before any
code changes: identifiers and attempt boundaries, the execution-context contract, the transition-fact feed, the
projection model, budgets, error categories and the operator authority. Later steps implement it; a change after
acceptance needs an amendment.

## Context

Operators cannot follow one tool call across the Gateway, Control, the Tool Host and an endpoint client, and have no
aggregate view of tool usage, latency or failures across tenants. The pieces exist but are not joined:

- The Gateway validates or generates a W3C `traceparent` and a `gw-…` request ID ([http.rs](../../apps/gateway/src/http.rs)).
  Without an incoming parent the sampled flag is `00`, and `tracestate` is dropped.
- `ToolInput.traceparent` exists, but the Tool Host and endpoint client set it to `None`; the conformance case
  `mcp-core/trace-propagation` therefore fails.
- `ToolInput.protocolVersion` is the constant `2`. The Rust and PHP contract decoders reject unknown fields, but the
  consumers of `ToolInput` are the SDK runtimes inside the sandbox, and both shipped runtimes (Java `Governed`, Python
  `governed.py`) check only `protocolVersion` and ignore members they do not know. Control, Gateway, Tool Host and
  managed clients ship as matching versions ([upgrades.md](../control-plane/upgrades.md)).
- The signed permit already carries an `attempt` claim, which the Tool Host passes to the tool; the Gateway requests
  attempt `1` for every reservation.
- Control owns the ledger ([invocation-state-v2.md](../control-plane/invocation-state-v2.md)). Each transition is one
  transaction with an expected revision and audit. Transition history in `task_document.transitions` is capped at 64,
  and run events are capped and expire after seven days, so neither is a complete history.
- The **fencing token is the consumed permit nonce**. It authorises secret delivery, broker capabilities, heartbeats
  and result reports (invocation-state-v2 §5). The run-event `attempt` number is reported by the executor.
- `invocationId` is generated by the Gateway (platform-requirements.md §12.7 row 2). `agentId` and `userId` come from
  verified identity (enterprise-access-control.md), not from caller metadata.
- `SUPER_ADMIN` is resolved from a **tenant's** directory (`ManagementAccess.superAdministrator(directory, user)`, ADR
  022). There is no installation-level HTTP authority: tenant administration is a local operator command
  ([tenant-operations.md](../control-plane/tenant-operations.md)).
- The Gateway has an audit queue setting but no durable per-request record of denials.

## Decision

### 1. Identifiers

| Field | Source | Trust | Notes |
| --- | --- | --- | --- |
| `tenant_id` | Authenticated tenant context | Verified | |
| `client_id` | Gateway credential | Verified | |
| `user_id` | Verified identity | Verified | Absent for SERVICE calls |
| `agent_id` | Verified identity (`agentId`) | Verified | The plan listed it as declared; it is verified |
| `invocation_id` | Gateway-generated `invocationId` | Authoritative | Existing; one per admitted invocation |
| `execution_id` | Derived from the fencing token (below) | Authoritative | One per consumed permit |
| `attempt_number` | The permit's signed `attempt` claim | Authoritative | Control assigns it at T4 (below) |
| `tool_call_id` | Caller `_meta` / header; generated `tc-…` if absent | Declared | Correlation reference only |
| `session_id`, `agent_run_id` | Caller `_meta` / header | Declared | `Mcp-Session-Id` is never used as `session_id` |
| `parent_invocation_id` | Propagated context, same tenant only | Declared | Step 6 |
| `trace_id`, `span_id` | W3C trace context or generated | Untrusted input | Never business identity |
| `request_id` | Gateway `gw-…` | Authoritative | Existing |
| `control_request_id` | Control `Correlation` UUID | Authoritative | Recorded next to `request_id` |

**Execution ID never exposes the fencing token.** The fencing token is a capability, so it must not appear in
summaries, spans, logs, exports or the UI. Control derives

```
execution_id = "ex-" + lowercase hex of SHA-256("toolgate-execution-v1" || 0x00 || tenantId || 0x00 ||
               invocationId || 0x00 || fencingToken), first 32 characters
```

The nonce has full entropy, so the digest does not reveal it. Every component that holds the token computes the same
ID with no extra wire field: the Tool Host and endpoint client put it in `executionContext` (§2), and Control computes
it for facts (§4). `tests/fixtures/contracts/execution-id-vectors.json` holds the vectors every implementation must
reproduce.

**Attempt boundaries.** An attempt is one consumed permit (T5). Its number is the permit's signed `attempt` claim,
which executors already read. Step 3 makes Control assign that claim: it keeps `insights_attempts` on the invocation
row, increments it each time it reserves a permit (T4), and signs that value instead of the requested one (today
always `1`). A reserved permit that expires unconsumed (T12) uses a number without becoming an attempt, so numbers
may skip; they never repeat. A relayed device call has one attempt.

| Situation | Attempts |
| --- | --- |
| Ledger tool (`NON_IDEMPOTENT`, `UNKNOWN`) | Exactly one: T5 happens once and the row is never reclaimed |
| Non-ledger task re-queued after lease loss (T11, attempt < 3) | Each re-queue → T4 → T5 is a new attempt |
| T10 refusal before start | Counts as an attempt with outcome `NOT_STARTED` |
| Reconnect or result redelivery under the same fencing token | Same attempt |
| Stale-token report (newer attempt exists) | Evidence only; no new attempt |
| Caller resubmission with the same idempotency key / business key | No new invocation and no new attempt; the existing invocation answers |
| Caller reusing `tool_call_id` without an idempotency key | New invocation; both searchable by `tool_call_id` |
| Approval, queueing, reservation (T1–T4) | No attempt |

Step 3 verifies this table against the M5 dedup and reconciliation code paths with tests before projections rely on it.

### 2. Execution-context contract

- **No new tool protocol version.** `ToolInput` (tool protocol 2) gains one optional member, `executionContext`:
  `{executionId?, attemptNumber?, toolCallId?, sessionId?, agentRunId?, parentInvocationId?, tracestate?}`. The
  executor always sets `executionId` and `attemptNumber` from its permit and never takes them from the caller.
  Runtimes must ignore `ToolInput` members they do not know (conformance case `stdin/v2-execution-context`); both
  shipped SDK runtimes already do, so packages built with older SDKs keep running and simply do not read it. A bump to
  protocol 3 was rejected: it would need package-range negotiation for no behavioural gain.
- Platform hops carry the same object. `Dispatch` (Gateway to Tool Host, direct or relayed through Control) and the
  device relay messages `RemoteToolSubmission` / `RemoteToolTask` gain optional `traceparent` and `executionContext`.
  No negotiation is needed, because platform components ship as matching versions.
- Declared IDs use the contract `DeclaredId`: `^[a-zA-Z0-9][a-zA-Z0-9._:/@_-]{0,127}$`, which admits model tool-call
  IDs such as `call_…` and `toolu_…`. Invalid or duplicated values are dropped, never rejected; they never affect
  admission.
- Ingress: HTTP headers `Toolgate-Tool-Call-Id`, `Toolgate-Session-Id`, `Toolgate-Agent-Run-Id`; MCP `_meta` keys
  `io.ololabs.toolgate/toolCallId`, `…/sessionId`, `…/agentRunId`. `_meta` wins over headers.
- Trace context: a valid `traceparent` header wins; otherwise a valid `traceparent` in `_meta` (MCP trace context) is
  continued. Each hop (Gateway, Tool Host, device) keeps the trace ID and sampled flag and uses its own span ID.
  `tracestate` travels only with the parent it arrived with, up to 512 bytes and 32 members, otherwise it is dropped.
  Baggage is not propagated.
- Every `tools/call` result names its invocation in `_meta["io.ololabs.toolgate/invocationId"]`; every response
  already carries `X-Request-Id`.
- SDKs expose the context read-only (Java `Invocation.executionId()`, `toolCallId()`, `sessionId()`, `agentRunId()`,
  `traceparent()`, `traceHeaders()`; Python equivalents), and `attempt` reads `attemptNumber`. `traceHeaders()` returns
  only W3C headers, never user, session or tool identifiers.
- Changes follow the contract generation rules (ADR 001): canonical schema, generated bindings, fixtures and the
  conformance case together.

### 3. Collection modes

`TOOLGATE_INSIGHTS_MODE=NONE|BASIC|DETAILED`, default `NONE`, read by Control, Gateway, Tool Host and endpoint client
(the last two receive it from Control configuration). Invalid values fail startup. In `NONE`, no Insights table or
column is written and no Insights span is produced. Platform tracing (`TraceRedaction`,
`toolgate.control.trace-export-enabled`) is unaffected by the mode.

### 4. Transition facts

- Migration (appended, both databases): `control_enterprise_invocations` gains `insights_fact_seq bigint NOT NULL
  DEFAULT 0` and `insights_attempts integer NOT NULL DEFAULT 0`.
- Table `insights_transition_fact`, primary key `(tenant_id, invocation_id, fact_seq)`, partial index on unprojected
  rows; no other indexes.
- Written for T1–T5 and T7–T13 in the transition's own transaction. Not written for T6 (lease renewal) or T14 (purge).
  The transition's existing `UPDATE` of the invocation row increments `insights_fact_seq` (and `insights_attempts` at
  T4, §1); the fact uses the new values.
- Atomic with the ledger, like the audit row: an insert failure fails the transition, which retries under the existing
  policy. There is no fail-open path.

Field-to-fact sources:

| Summary field | Fact source |
| --- | --- |
| tenant, client, user, agent, tool ID/version, runtime, effect safety | T1 `context` |
| `tool_call_id`, `session_id`, `agent_run_id` and provenance | T1 `context` |
| accepted time | T1 `occurred_at` |
| approval requested / resolved | T1 (to `PENDING_APPROVAL`) / T2, T3 `occurred_at` |
| queued | T1 (to `QUEUED`), T2, T11 (re-queue) `occurred_at` |
| reserved | T4 `occurred_at` |
| attempt start, `execution_id`, `attempt_number`, executor kind and ID | T5 |
| executor and SDK protocol range of the package | T5 |
| input waits | T7 `occurred_at` pairs |
| cancel requested | T8 `occurred_at` |
| attempt end, executor duration, attempt outcome | T9, T10 |
| attempt lost (lease expiry) | T11 |
| terminal state, outcome, error category, terminal time | T3, T8 (direct cancel), T9, T10, T11, T12 |
| outcome correction | T13 |

Fields with no source here (for example executor queue position) are not shipped.

### 5. Projection

- Projector partitions: 16, by `hash(tenant_id, invocation_id)`. Leases in `insights_projector_lease(partition, owner,
  epoch, expires_at)`, 30 s, renewed every 10 s; every batch re-checks `owner` and `epoch` before commit. Workers: up
  to 4 per Control replica on PostgreSQL; 1 on SQLite.
- Batch: up to 500 facts; per-invocation fold, per-cell sum, one transaction, cell upserts in sorted key order.
  Checkpoint rows are locked and `last_fact_seq` re-read inside the transaction.
- Checkpoint `insights_projection_checkpoint(tenant_id, invocation_id, last_fact_seq, contribution, final)`; deleted
  together with the invocation's facts by one retention transaction once the invocation is final (terminal and not
  `OUTCOME_UNKNOWN`), every fact is projected, and fact retention has passed.
- Aggregates: `by_tool (tenant, tool, runtime, outcome)` and `by_client (tenant, client, outcome)` at minute, hour and
  day, written directly by every contribution change. Buckets use the invocation's accepted time, UTC, half-open.
- Duration histogram bounds (ms): 1, 2, 5, 10, 20, 50, 100, 200, 500, 1 000, 2 000, 5 000, 10 000, 30 000, 60 000,
  120 000, 300 000, 600 000, 1 800 000, 3 600 000, +∞. Percentiles interpolate within a bucket and are reported with
  that bucket's bounds as their error. p95 needs 20 samples, p99 needs 100.
- Admission counters: Control-side decisions counted in Control (complete); Gateway-side decisions sent as delta
  batches keyed `(gateway_id, epoch, seq)`, flushed every 10 s, best-effort with source-gap reporting.

### 6. Retention, quota and budgets

| Item | Default | Bounds |
| --- | --- | --- |
| Transition facts | 7 days after the invocation is final | 0–30 days, ≤ summary retention |
| Invocation and attempt summaries | 30 days | 1–90 days |
| Minute / hour / day aggregates | 48 hours / 90 days / 13 months | configurable, coarser ≥ finer |
| Local span store | 72 hours | 1–14 days |
| Span buffer per Control replica | 64 MiB | 8–512 MiB |
| Spans per invocation / bytes per invocation | 512 / 512 KiB | |
| Insights storage quota | 10 GiB | operator-set |

Overhead budgets are **provisional** until the step 3 baseline:

| Measure | Budget |
| --- | --- |
| Added p95 commit latency per transition, PostgreSQL | ≤ 2 ms |
| Added p95 commit latency per transition, SQLite | ≤ 5 ms |
| Added p99 end-to-end invocation latency, `BASIC` | ≤ 3% |
| Added p99 end-to-end invocation latency, `DETAILED` | ≤ 7% |
| Projector lag at sustained peak | ≤ 30 s p95 |
| Control CPU for span handling at peak, `DETAILED` | ≤ 10% of one core per 100 invocations/s |

If a measured value misses its budget, the step 3 PR either meets it or amends this ADR with the measured value and
the reason. Capture is never made best-effort to meet a budget.

### 7. Error categories

Every terminal failure gets exactly one category. Shared `ErrorCode` values map as follows; codes specific to v2 are
mapped in step 3, where a contract test fails on any code without a category.

| Category | Includes |
| --- | --- |
| `POLICY` | `FORBIDDEN`, `UNAUTHORIZED`, approval denied or revoked (T3), kill switch |
| `TIMEOUT` | `TIMEOUT`, deadline or lease expiry (T11 to `FAILED`, T12) |
| `CANCELLED` | T8 outcomes |
| `TOOL_ERROR` | Tool reported `FAILED` with a tool error |
| `INFRASTRUCTURE` | `DEPENDENCY_UNAVAILABLE`, `INTERNAL`, `TENANT_UNAVAILABLE`, `MISDIRECTED_REQUEST`, dispatch or executor failure, T10 refusal |
| `INVALID_REQUEST` | `VALIDATION`, `NOT_FOUND`, `CONFLICT`, `UNSUPPORTED`, `TENANT_MISMATCH`, `INVALID_TENANT_ID` |
| `PARTIAL` | `PARTIAL` state, `PARTIAL_OUTCOME` |
| `UNKNOWN` | `OUTCOME_UNKNOWN` |

### 8. Operator authority

Tenant roles, including `SUPER_ADMIN`, cannot grant Insights access, because they are resolved from one tenant's
directory and Insights spans all tenants. Insights therefore needs an installation-level authority, which does not yet
exist over HTTP.

**Proposed:** Control serves the Insights API and page on a separate **operator listener**, disabled unless
configured, bound to a private address like the management listener (port 9092). It authenticates operators with
client certificates issued from an installation operator CA held under the same custody rules as other operator
files. It is never routed through tenant ingress (8082), and no tenant credential is accepted on it. Self-hosted
customers configure the same listener for themselves. Every Insights request writes installation-scope audit.

This is the one decision that needs explicit review before step 3, because it adds a new authority to Control.

### 9. Spans (step 5)

Control is the only Insights span sink and exporter. Retention is a deterministic function of outcome, elapsed time
and `hash(invocation_id)`; invocations that pass their slow threshold are flushed early; buffers are bounded per
replica. Endpoint and host uploads use the run-event authentication and fencing checks, and Control rewrites resource
identity from the authenticated certificate.

## Alternatives Considered

- **Fencing token as execution ID:** rejected; it is a capability and would leak through telemetry.
- **Executor-reported attempt number:** rejected for Insights; Control assigns it in the signed permit at T4.
- **Tool protocol 3 for `executionContext`:** rejected; runtimes already ignore unknown members, so an optional member
  needs no package-range negotiation.
- **Timestamp or revision scan instead of facts:** rejected; misses intermediate transitions.
- **Fail-open fact insert with savepoints:** rejected; the failures that stop it stop the ledger write too.
- **Compaction of finer into coarser rollups:** rejected; late corrections would need reopened buckets.
- **Collector tail sampling:** rejected for the first release; the local waterfall would need a Collector.
- **`SUPER_ADMIN` as operator:** rejected; tenant-scoped.
- **Tenant-scoped Insights for tenant administrators:** out of scope; telemetry is for installation operators.

## Security Impact

- New installation-level operator authority (§8) with its own CA and listener; no tenant credential reaches it.
- Fencing tokens never leave their existing paths; `execution_id` is a one-way digest.
- Declared metadata and trace context never change authentication, routing, policy or approval.
- Insights stores metadata only. Error text, URLs and locators pass the existing run-event redaction plus an
  attribute allowlist; arguments, outputs and secrets are never stored.
- Span uploads are bound to the device and fencing token of the invocation, like run events.

## Operational Impact

- New setting `TOOLGATE_INSIGHTS_MODE` (default `NONE`), retention and quota settings, operator listener settings.
- New tables and two columns on the invocation table; migrations for PostgreSQL and SQLite.
- Projector leases, lag, storage use and drops are exposed on the status endpoint and as health metrics.
- `BASIC`/`DETAILED` add one row per state-changing transition to the ledger transaction.

## Compatibility Impact

- `executionContext` is an optional `ToolInput` member within tool protocol 2; runtimes that predate it ignore it. Platform hops gain optional members and ship as matching versions.
- New ingress headers and `_meta` keys are optional.
- No change to existing APIs, run events or audit records.

## Consequences

- Positive: one execution identity across components; usage numbers derived from the ledger; no new infrastructure.
- Negative: one extra write per transition when enabled; a new operator authority to operate; summaries and spans
  have bounded retention.

## Validation

The release gates in plan.md §9, run together in the integration testing stage, and specifically:

- `mcp-core/trace-propagation` passes; a package built with an older SDK still runs when it receives `executionContext`.
- No fencing token appears in any Insights table, span, log, export or response (canary test).
- Projections equal the ledger after replay, crashes, concurrent workers, T11 re-queues and T13 corrections.
- Measured overheads meet §6 or this ADR is amended with the measurements.
- Non-operators and tenant credentials are refused on every Insights endpoint.
